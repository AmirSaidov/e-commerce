# Решения, принятые на стороне бэкенда

Фронтенд (https://github.com/AmirSaidov/e-commerce) не меняется; если ТЗ и код фронта расходятся,
бэкенд следует коду фронта.

## Этап 1 — каркас

1. **Корень репозитория = папка `backend/` из ТЗ.** `manage.py`, `config/`, `apps/` лежат прямо в корне
   репозитория бэкенда, без лишнего уровня вложенности.
2. **Настройки — один модуль `config/settings.py`**, всё переменное читается из `.env` через
   `django-environ` (он же разбирает `DATABASE_URL` и `EMAIL_URL=consolemail://` из `.env.example`),
   поэтому отдельный `dj-database-url` не нужен. Различия dev/prod завязаны на `DEBUG`.
3. **`User.avatar`.** Тип `User` на фронте содержит `avatar: string | null`, в ТЗ этого поля нет.
   Добавлено необязательное `ImageField`; загрузки аватара нет (по ТЗ), в ответах будет `null`.
4. **Email без учёта регистра.** Email приводится к нижнему регистру целиком при сохранении, поэтому
   `Demo@Voltra.kz` и `demo@voltra.kz` — один пользователь.
5. **Формат ошибок** (`apps/core/exceptions.py`), всегда `{detail, code, fields}`:
   - ошибки полей сериализатора уходят в `fields`, `detail` = «Проверьте правильность заполнения полей.»,
     `code` = `validation_error`;
   - `non_field_errors` поднимаются в `detail` (с их `code`, если он задан), а в `fields` не попадают:
     фронт (`form-errors.ts`) считает любую запись в `fields` ошибкой конкретного поля формы и тогда
     не показывает тост;
   - вложенные ошибки (например, позиции заказа) получают ключи вида `items.1.quantity`;
   - необработанные исключения при `DEBUG=False` отдают `500` с `code: server_error`, неизвестные URL
     возвращают `404` JSON (обработчики `handler404/500` в `config/urls.py`).
   - Для своих ошибок с кодом есть `ApiException(detail, code=..., status_code=...)`.
6. **Права по умолчанию — `IsAuthenticated`.** Публичные эндпоинты (каталог, регистрация, `apply-promo`
   и т.п.) явно помечаются `AllowAny`.
7. **Cookie refresh-токена:** `refresh_token`, `Path=/api/v1/auth/`, `HttpOnly`. В проде
   `Secure; SameSite=None`, при `DEBUG` по умолчанию `Secure=False; SameSite=Lax` (localhost:3000 и
   localhost:8000 — один сайт). Оба значения можно переопределить через `REFRESH_COOKIE_SECURE` и
   `REFRESH_COOKIE_SAMESITE`.
8. **Служебные эндпоинты:** `GET /api/v1/health/` для health-check на Render/Railway, OpenAPI-схема
   на `/api/schema/`, Swagger UI на `/api/docs/`.
9. **Валюта Stripe** вынесена в настройку `STRIPE_CURRENCY` (по умолчанию `kzt`), подробности будут
   на этапе 7.

## Этап 2 — авторизация

1. **Коды ошибок авторизации** (совпадают с мок-бэкендом фронта `frontend/src/lib/mock/backend.ts`):
   - неверный email/пароль или неактивный пользователь — `401 invalid_credentials`,
     «Неверный email или пароль.»;
   - email не подтверждён — `403 email_not_verified`. Статус раскрывается только при верном пароле;
   - битая или устаревшая ссылка из письма — `400 invalid_token`;
   - нет refresh-cookie — `401 not_authenticated`; refresh недействителен, отозван или пользователь
     отключён — `401 token_not_valid`, при этом cookie удаляется;
   - чужой `Origin` на refresh/logout — `403 origin_not_allowed`.
2. **Эндпоинты `/auth/*` не читают заголовок `Authorization`.** Фронт шлёт logout с Bearer-токеном;
   если access уже истёк, logout всё равно должен пройти, а не отдать 401.
3. **Повторная отправка письма подтверждения.** На фронте нет кнопки «отправить ещё раз», поэтому
   при попытке входа с верным паролем, но неподтверждённым email письмо отправляется снова
   (не чаще раза в 5 минут на пользователя).
4. **Токен подтверждения email** — тот же механизм `PasswordResetTokenGenerator` (`uid` +
   `urlsafe_base64_encode(pk)`), но со своей солью: ссылка подтверждения не годится для сброса пароля
   и наоборот. Для сброса пароля используется ровно `default_token_generator` (ссылка одноразовая).
   Повторный переход по ссылке подтверждения отдаёт `204`.
5. **Сброс пароля:**
   - `POST /auth/password-reset/` отдаёт `204` и для несуществующего email; некорректный формат email —
     обычная ошибка валидации `400` (фронт эту ошибку всё равно игнорирует);
   - страница `/password-reset/confirm` на фронте показывает только `detail`, поэтому ошибки
     валидаторов пароля лежат в `fields.password`, а первая из них дублируется в `detail`;
   - после сброса все refresh-токены пользователя отзываются, а email считается подтверждённым
     (ссылка пришла на эту почту).
6. **Проверка `Origin` на refresh и logout.** Cookie с `SameSite=None` браузер отправит с любого
   сайта, поэтому запросы с `Origin` не из `CORS_ALLOWED_ORIGINS` (и не с домена самого API)
   отклоняются. Запросы без `Origin` (curl, серверные компоненты Next) проходят.
7. **Лимиты частоты** — см. раздел «Лимиты частоты» ниже.
8. **Время жизни токенов:** access — 15 минут, refresh — 14 дней (`ACCESS_TOKEN_MINUTES`,
   `REFRESH_TOKEN_DAYS`). Ссылки из писем действуют 3 дня (`PASSWORD_RESET_TIMEOUT` Django).
9. **Сбой SMTP не ломает запрос:** регистрация и сброс пароля отвечают как обычно, ошибка пишется в лог.
10. **Тексты DRF на английском:** сообщение парсера JSON («JSON parse error - …») заменяется
    на «Не удалось разобрать тело запроса.».

## Лимиты частоты на /auth/

- **Что ограничено:** вход 10/мин, регистрация 10/час, сброс пароля 5/час с одного IP (прод).
  Ставки задаются в `.env`: `THROTTLE_LOGIN`, `THROTTLE_REGISTER`, `THROTTLE_PASSWORD_RESET`.
  Пустое значение отключает лимит. Превышение — `429` с `code: throttled`.
- **Режим тестов:** `THROTTLE_RELAXED` (по умолчанию равен `DEBUG`) ставит всем трём 1000/мин,
  чтобы e2e-сценарии фронта (много входов подряд) не упирались в лимит. Если e2e гоняются против
  сборки с `DEBUG=False`, задайте `THROTTLE_RELAXED=True`. В pytest лимиты ослабляет `conftest.py`,
  а тесты самого лимита задают строгую ставку явно.
- **Свой класс `AuthRateThrottle`** (`apps/core/throttling.py`): стандартный `ScopedRateThrottle`
  читает ставки один раз при импорте, поэтому их нельзя переопределить ни в тестах, ни без перезапуска.
- **Где хранятся счётчики:** в кэше Django (`CACHES["default"]`, переменная `CACHE_URL`).
  По умолчанию `LocMemCache` — память процесса. Там же лежит пауза между повторными письмами
  подтверждения email.
- **Ограничения при нескольких воркерах:** у `LocMemCache` у каждого процесса gunicorn свои счётчики.
  При N воркерах реальный лимит до N раз выше заявленного, и сбрасывается при перезапуске.
  Для общего счётчика без Redis (по ТЗ Redis не используем) достаточно `CACHE_URL=dbcache://django_cache`
  и одного запуска `python manage.py createcachetable`: счётчики лягут в таблицу PostgreSQL ценой
  пары лишних запросов на каждый вход.
- **IP клиента:** DRF берёт его из `X-Forwarded-For`, а без него — из `REMOTE_ADDR`. За прокси
  Render/Railway это адрес клиента, но заголовок можно подделать. Для портфолио-проекта это
  приемлемо; при необходимости задаётся `NUM_PROXIES` в `REST_FRAMEWORK`.

## Этап 3 — каталог и seed

1. **Сверка с моком фронта.** Правила взяты из `frontend/src/lib/mock/catalog.ts` (это код фронта,
   он важнее ТЗ). Тест `test_seed_matches_frontend_mock` прогоняет seed на настоящем `catalog.json`
   и проверяет, что цены, `default_variant`, `in_stock`, рейтинги и число отзывов совпадают с демо-режимом.
2. **Цены вариантов:** `price + delta`, `old_price + delta` (как в моке).
3. **Артикулы:** в моке `SLUG[:10]-N`, и это даёт коллизии (`SAMSUNGGAL-1`, `MICROSOFTX-1`),
   а `sku` уникален. В seed используется полный slug: `SAMSUNG-GALAXY-S25-ULTRA-1`.
4. **Рейтинг и отзывы.** В `catalog.json` есть `rating`, но в мок-режиме фронт показывает рейтинг,
   посчитанный по сгенерированным отзывам. Seed создаёт те же отзывы (8 неактивных демо-авторов без
   пароля, те же тексты и оценки), а `rating`/`reviews_count` пересчитываются сигналами на
   сохранение/удаление `Review`. Поэтому числа совпадают с демо-режимом, а `review_exists` /
   `review_not_purchased` (этап 8) будут работать на реальных данных.
5. **`created_at` товара** — дата из `created` в полночь UTC (как `new Date("2026-09-20")` во фронте).
   В JSON отдаётся во времени Asia/Almaty: `2026-09-20T05:00:00+05:00`.
6. **`/products/{slug}/related/`.** ТЗ: «та же категория». Мок фронта: сначала та же категория, затем
   соседние подкатегории того же родителя, до 8. Реализовано как в моке; внутри групп — по популярности.
7. **Поиск** (`search` в списке и `/products/search/?q=`) — подстрока каждого слова в названии,
   бренде, категории или описании (`icontains`), все слова обязательны. Так же ищет мок, и это
   работает на недописанных словах в подсказках (`iph` → iPhone), где полнотекстовый поиск со
   стеммингом ничего не найдёт. На SQLite регистр не учитывается только для латиницы; на PostgreSQL —
   и для кириллицы (тест помечен как Postgres-only). Если каталог вырастет, следующий шаг —
   GIN-индекс `pg_trgm` на этих полях, контракт при этом не меняется.
8. **`default_variant`, цена, `in_stock`** считаются в SQL через подзапросы (`Subquery`/`Exists`):
   по ним работают `price_min/max`, `on_sale`, `in_stock` и сортировка по цене. Список товаров — 3 запроса
   независимо от размера страницы (COUNT, SELECT, prefetch вариантов), есть тест на N+1.
9. **`on_sale`** — у default-варианта есть `old_price` (как в ТЗ и моке). `in_stock=false` /
   `on_sale=false` не фильтруют (фронт передаёт только `true`).
10. **Товары без вариантов и неактивные** в каталог не попадают: фронт ждёт `default_variant` всегда.
11. **Каталог не читает `Authorization`** (`authentication_classes = []`): серверные компоненты Next
    ходят без токена, а просроченный токен в браузере не должен ломать витрину.
12. **Неверные параметры** (`ordering=name`, `price_min=abc`) — `400` с ошибкой в `fields`;
    страница за пределами — `404 not_found`.
13. **Seed:** `python manage.py seed [--catalog PATH] [--images DIR]`, по умолчанию клон фронта в
    `../frontend-readonly`. Идемпотентен (поиск по slug/sku/email/(товар, автор)); при повторном запуске
    данные каталога, остатки и пароль демо-пользователя возвращаются к значениям из файла. Картинки
    копируются через хранилище Django (`default_storage`) и уже скопированные не перезаписываются,
    поэтому команда будет работать и с Cloudinary/R2. Файлы фронта не изменяются. Промокоды
    добавятся в seed на этапе 5 вместе с моделью `PromoCode`.
14. **Логотипов брендов** в данных фронта нет — `logo: null` (как в моке).
15. **Модели `Review` и `ReviewImage`** созданы сейчас (ТЗ относит их к каталогу, seed создаёт отзывы),
    эндпоинты отзывов — этап 8.

## Этап 4 — профиль, пароль, адреса, избранное

1. **`/users/me/`** — `GET` и `PATCH` (`PUT` → 405). Меняются только `first_name`, `last_name`, `phone`;
   `email`, `avatar`, `is_email_verified`, `id` в PATCH молча игнорируются. Валидация повторяет
   `profileSchema` фронта (`frontend/src/lib/validation.ts`): имя и фамилия не пустые, до 50 символов;
   телефон `^\+?[\d\s()-]{10,20}$` или пустая строка; тексты ошибок — те же, что на фронте.
2. **Без токена или с просроченным access** — `401` (`not_authenticated` / `token_not_valid`), а не `403`:
   по 401 фронт один раз обновляет access-токен и повторяет запрос.
3. **`POST /users/me/password/`:** неверный старый пароль — `fields.old_password`
   «Текущий пароль указан неверно.» (как в моке); слабый новый — тексты валидаторов Django в
   `fields.new_password`. После смены все refresh-токены пользователя отзываются (другие устройства
   разлогиниваются), а текущий браузер в том же ответе `204` получает новую refresh-cookie
   (`Path=/api/v1/auth/` можно выставить из ответа на любой URL), поэтому пользователя не выкидывает,
   когда истечёт access.
4. **Адрес:** поля из типа `Address` фронта (`city, street, building, apartment, postal_code,
   is_default`) — получателя и телефона в адресе нет. Индекс — 6 цифр или пусто, квартира — до 10
   символов (как `addressSchema` фронта).
5. **Основной адрес** — правила мока `saveAddress` / `deleteAddress`: первый адрес становится основным;
   `is_default=true` сбрасывает флаг у остальных; `is_default=false` у основного адреса игнорируется
   (основной есть всегда); при удалении основного основным становится самый старый из оставшихся.
   Изменения идут в транзакции с блокировкой строки пользователя, а частичный уникальный индекс
   `users_address_one_default` гарантирует не больше одного основного адреса на уровне БД.
6. **Лимит адресов** — 20 на пользователя (`400 address_limit`), защита от мусора. Список адресов —
   в порядке создания, без пагинации. Чужой адрес — `404`, а не `403`.
7. **Избранное:** `POST /wishlist/` и `DELETE /wishlist/{product_id}/` отвечают `204` без тела
   (фронт ждёт `void`) и идемпотентны. Несуществующий или неактивный товар при добавлении —
   `400`, `fields.product_id` «Товар не найден.». Список — `ProductListItem[]` без пагинации,
   последние добавленные сверху (как `unshift` в моке); неактивные товары из списка пропадают.
   Список избранного — 3 запроса независимо от числа товаров (тест на N+1).
8. **Seed сбрасывает профиль демо-пользователя** (имя, фамилия, пустой телефон, пароль), чтобы
   демо-аккаунт после экспериментов можно было вернуть в исходное состояние повторным `seed`.
   Адреса и избранное демо-пользователя seed не трогает.

## Этап 5 — корзина и промокоды

1. **Корзина живёт на фронте, сервер её только синхронизирует.** `POST /cart/merge/` (сразу после
   входа) берёт максимум количества для совпадающих вариантов, как `mergeCart` в моке, и возвращает
   `ServerCart`. `PUT /cart/` полностью заменяет корзину и отвечает `204`.
2. **Устаревшие позиции отбрасываются молча.** Фронт игнорирует ошибки `PUT /cart/`, а в
   localStorage гостя могут лежать id вариантов, которых уже нет. Поэтому неизвестные варианты и
   товары, снятые с продажи, пропускаются, а не валят весь запрос `400`. Повторы одного варианта в
   `PUT` складываются.
3. **`merge` ограничивает количество остатком и не возвращает закончившиеся товары.** Мок в этом
   случае отдаёт позицию с `quantity: 0`, которую потом нельзя оформить (`quantity ≥ 1`), поэтому
   на бэке такие позиции убираются. Это расхождение с моком — в списке для владельца фронта.
4. **Скидка** считается как `calcPromoDiscount` фронта: `min(round(raw), subtotal)`, округление
   половины вверх (`Math.round`), где `raw = subtotal × value / 100` для процента или `value` для
   суммы. Тест сверяет граничные случаи (1.5 → 2, 1.4 → 1).
5. **Тексты ошибок промокода — из мока фронта** (ТЗ приводит «Промокод не найден», но код фронта
   важнее): «Такого промокода нет.» (`promo_not_found`), «Срок действия промокода истёк.»
   (`promo_expired`). Дополнительно: `promo_inactive` и `promo_exhausted` — «Промокод больше не
   действует.», `promo_min_subtotal` — «Промокод действует для заказов от 100 000 ₸.».
6. **`apply-promo` открыт гостям**, не читает `Authorization` и ничего не пишет в БД (один SELECT).
   Против перебора кодов — лимит 30/мин с IP (`THROTTLE_PROMO`), тем же механизмом, что на `/auth/`.
7. **Код промокода** хранится в верхнем регистре, ввод не чувствителен к регистру и пробелам по краям.
   Процентный промокод не может быть больше 100 % (CHECK в БД).
8. **Seed** создаёт `WELCOME10` (−10 %), `VOLTRA5000` (−5 000 ₸) и `SUMMER25` (−25 %, истёк 31.08.2025).

## Этап 6 — заказы

1. **Состав заказа — из запроса, всё остальное — из БД.** `items` приходят от фронта (без гонки с
   debounce-синхронизацией корзины), но цены, остатки, скидка и доставка считаются на сервере.
   Любые `price`/`subtotal`/`discount` в теле запроса игнорируются. Повторы одного варианта складываются.
2. **Списание остатков:** одна транзакция; варианты блокируются `select_for_update(of=("self",))` в
   порядке id (без дедлоков между параллельными заказами, блокируются только варианты, а не товары);
   списание — `UPDATE … SET stock = stock - N`. Дополнительная страховка — `stock` это
   `PositiveIntegerField` с CHECK `stock >= 0` в БД.
3. **Нехватка остатка — `400 out_of_stock`**, текст как в ТЗ: «„AirPods Pro 2“ осталось только 2 шт.».
   Если у товара несколько вариантов, добавляется вариант: «„Apple iPhone 16 Pro, 512 ГБ“ осталось
   только 2 шт.» — иначе непонятно, чего не хватает (у 128 ГБ остаток может быть большим). При нуле —
   «„PlayStation 5“ закончился.». Товар снят с продажи или вариант удалён — `400 variant_not_found`.
   Пустой список — `400 cart_empty` «Корзина пуста.» (как в моке).
4. **Доставка — как `calcDeliveryPrice` фронта:** курьер `COURIER_PRICE` (1 500 ₸), бесплатно, если
   сумма **после скидки** ≥ `FREE_SHIPPING_FROM` (100 000 ₸); самовывоз 0 ₸. Значения из `.env`.
5. **Адрес:** для курьера `address_id` обязателен (`400 address_required` «Укажите адрес доставки.»)
   и должен принадлежать пользователю (`400 address_not_found`). Фронт присылает `address_id` и при
   самовывозе — тогда он игнорируется, `address: null`. `Order.address` — снимок
   `{city, street, building, apartment, postal_code}`: изменение или удаление адреса заказ не меняет.
6. **Промокод проверяется заново.** Неверный, истёкший, неактивный, исчерпанный или не проходящий
   по минимальной сумме промокод — `400` с тем же кодом, что у `apply-promo`, и заказ **не создаётся**.
   Мок фронта в этом случае молча оформляет заказ без скидки; молча взять больше денег, чем человек
   видел в корзине, хуже, поэтому бэк отказывает с понятным `detail` (фронт покажет его в тосте).
   Пустой `promo_code` игнорируется. Строка промокода блокируется на время транзакции, отменённые
   заказы в `usage_limit` не считаются.
7. **Номер заказа** — `VT-{ORDER_NUMBER_START + id}` (по умолчанию `VT-100001`, `VT-100002`, …):
   уникален и растёт вместе с id. После отката транзакции номер может «пропасть» (как и id).
8. **`OrderItem` — снимок:** название и slug товара, название варианта, sku, цена, количество,
   главное фото. В JSON — поля типа `OrderItem` фронта (`variant_id`, `product_slug` нужны для повтора
   заказа и проверки отзывов); `sku` хранится, но не отдаётся. Товары и варианты с заказами удалить
   нельзя (`PROTECT`) — их снимают с продажи `is_active=False`.
9. **После успешного заказа серверная корзина очищается целиком;** при ошибке — не трогается.
10. **Отмена** (`POST /orders/{number}/cancel/`) — только из `created` и `paid`, иначе
    `400 order_not_cancellable` «Этот заказ уже нельзя отменить.». Остатки возвращаются на склад,
    у оплаченного заказа откатывается `popularity`. Строка заказа блокируется — повторная
    параллельная отмена не вернёт остаток дважды. **Возврат денег за оплаченный заказ** в Stripe не
    делается автоматически (в ТЗ его нет) — это ручная операция в кабинете Stripe.
11. **Список и детали — только свои заказы**, новые сверху, `page_size` до 100. Чужой или
    несуществующий номер — `404` «Заказ не найден.» (текст мока).
12. **Админка:** вручную можно перевести заказ только в `assembling`, `shipped`, `delivered`.
    `paid` ставит только вебхук Stripe (этап 7), отмена — действием «Отменить заказы», которое
    возвращает остатки через тот же сервис.

## Что проверяется только на PostgreSQL

На SQLite эти тесты пропускаются (`skipif`), их нужно прогнать после подключения Postgres:

- `apps/orders/tests/test_concurrency.py` — параллельные запросы в отдельных потоках и транзакциях:
  последняя единица товара продаётся ровно один раз; остаток списывается точно при параллельных
  заказах; `usage_limit` промокода не превышается под гонкой; двойная параллельная отмена не
  возвращает остаток дважды; параллельное создание первых адресов даёт ровно один основной;
  параллельный первый `merge` не создаёт две корзины и не падает `500`.
- `apps/catalog/tests/test_products.py::test_search_cyrillic_case_insensitive` — поиск без учёта
  регистра для кириллицы (SQLite `LIKE` учитывает регистр не-ASCII символов).

Почему не на SQLite: SQLite игнорирует `select_for_update` и блокирует на запись всю базу, а
`of=("self",)` у `select_for_update` — синтаксис PostgreSQL. Корректность блокировок и поведение под
гонкой на SQLite не проверить.

## Этап 7 — Stripe Checkout

1. **Валюта — KZT, решение «тенге поддерживается».** По [docs.stripe.com/currencies](https://docs.stripe.com/currencies)
   все валюты двухзначные, если не указано иное; KZT нет среди zero-decimal и особых случаев, поэтому
   сумма передаётся в тиынах: 129 990 ₸ → `unit_amount = 12999000`. Валюта вынесена в `STRIPE_CURRENCY`
   (по умолчанию `kzt`); пересчёт в минорные единицы (`to_minor_units`) учитывает zero-decimal валюты,
   так что смена валюты не требует правок кода. **Проверить на настоящем Stripe:** что KZT доступна как
   валюта платежа для страны вашего Stripe-аккаунта (аккаунт в Казахстане Stripe не открывает —
   нужен аккаунт в поддерживаемой стране, деньги конвертируются в валюту счёта выплат). Если KZT
   окажется недоступна — `STRIPE_CURRENCY=usd` плюс конвертация цен, это отдельная задача.
2. **Минимальная сумма.** Stripe не примет платёж меньше ~0,50 USD в пересчёте в валюту счёта выплат.
   Для заказов меньше `STRIPE_MIN_AMOUNT` (по умолчанию 500 ₸, с запасом) `checkout-session` отвечает
   `400 amount_too_small` «Сумма заказа слишком мала для онлайн-оплаты…».
3. **Позиции Checkout Session — позиции заказа** (`«товар — вариант»`, цена и количество из снимка
   `OrderItem`) плюс строка «Доставка курьером», если она платная. Скидка по промокоду —
   разовый купон Stripe на сумму `Order.discount` (`amount_off`, `duration=once`, `max_redemptions=1`):
   строки Checkout не бывают отрицательными, а размазывать скидку по позициям — значит получить
   копеечные расхождения. Итог в Stripe всегда равен `Order.total` (проверено тестом).
4. **Ссылки на фронт:** `success_url = {FRONTEND_URL}/checkout/success?order={number}`,
   `cancel_url = {FRONTEND_URL}/account/orders/{number}`; `client_reference_id` и
   `metadata.order_number` — номер заказа; `customer_email` — email покупателя; `locale=ru`;
   ссылка живёт `STRIPE_SESSION_MINUTES` (60 минут).
5. **Повторное «Оплатить заказ»** создаёт новую сессию, а предыдущую закрывает
   (`checkout.sessions.expire`), чтобы заказ нельзя было оплатить по двум ссылкам.
   `Order.stripe_session_id` хранит последнюю сессию.
6. **Кому можно платить:** только свой заказ в статусе `created` с `payment_method=card`. Иначе:
   `payment_not_required` (оплата при получении), `order_already_paid`, `order_not_payable`; чужой или
   несуществующий — `404 «Заказ не найден.»`. Без `STRIPE_SECRET_KEY` — `503 payments_unavailable`
   (локально без ключей так и будет), ошибка Stripe API — `502 payment_provider_error` с текстом для тоста.
7. **Статус `paid` ставит только вебхук** `checkout.session.completed` (и
   `checkout.session.async_payment_succeeded` для асинхронных способов) при `payment_status=paid`.
   Подпись проверяется по `STRIPE_WEBHOOK_SECRET` (нет секрета — `503`, неверная/просроченная подпись —
   `400 invalid_signature`). Обработка под блокировкой строки заказа:
   - уже `paid` → ничего не делаем (идемпотентно: Stripe повторяет события);
   - сумма или валюта не совпали с заказом → не отмечаем оплату, ошибка в лог;
   - заказ отменён до прихода оплаты → не меняем статус, ошибка в лог «нужен ручной возврат»;
   - неизвестный заказ → ошибка в лог; на все такие случаи вебхук отвечает `200`, чтобы Stripe не
     повторял событие бесконечно.
   При переходе в `paid` `Product.popularity` растёт на количество; при отмене оплаченного — откатывается.
8. **Без сети в тестах.** Все вызовы Stripe собраны в `apps/payments/gateway.py`; тесты подменяют его
   функции. Вебхук в тестах подписывается локально тем же HMAC-SHA256, что у Stripe, и проходит через
   настоящую `stripe.Webhook.construct_event`.
9. **Возврат денег** при отмене оплаченного заказа автоматически не делается (в ТЗ нет) — вручную в
   кабинете Stripe по `Order.stripe_payment_intent`.

## Этап 8 — отзывы с фото

1. **`GET /products/{slug}/reviews/?page=`** — публично (не читает `Authorization`, как весь
   каталог), по 5 на страницу (`page_size` из запроса не принимается — как в моке), новые сверху.
   Неактивный или несуществующий товар — `404 «Товар не найден.»`. 4 запроса на страницу (тест на N+1).
2. **`POST /products/{slug}/reviews/`** — multipart `rating`, `text`, `images` (повторяющееся поле,
   до 5 файлов), только с JWT (без токена — `401`). Ответ `201` — `Review`.
3. **Порядок проверок как в моке:** сначала право на отзыв, потом форма.
   - `403 review_not_purchased` «Отзыв можно оставить только на полученный товар.» — нет своего
     заказа в статусе `delivered` с этим товаром (`created`/`paid`/`shipped`/`cancelled` не считаются);
   - `400 review_exists` «Вы уже оставили отзыв на этот товар.» — в том числе при гонке двух
     одинаковых отправок (уникальный индекс `(product, user)` → тот же ответ, а не `500`).
4. **Ошибки формы — в `detail`.** Форма отзыва на фронте показывает только тост с `detail`, поэтому
   первая ошибка валидации дублируется в `detail` (`fields` тоже заполнены). Правила — как
   `reviewSchema` фронта: оценка 1–5, текст 10–2000 символов, до 5 фото, каждое до 5 МБ, только
   JPEG/PNG/WEBP (формат проверяется по содержимому через Pillow, а не по расширению).
5. **Файлы фото** сохраняются под случайными именами `reviews/ГГГГ/ММ/<uuid>.<ext>`: имя файла
   пользователя в хранилище не попадает. EXIF (в том числе геометки) сейчас не вырезается — в
   кандидаты на доработку.
6. **`author`** — «Имя Ф.»; без фамилии — только имя; без имени — «Покупатель» (мок для пустой
   фамилии дал бы «Имя .»).
7. **Рейтинг товара** (`rating`, `reviews_count`) пересчитывается сигналами при создании и удалении
   отзыва (этап 3), в том числе при удалении из админки.
8. **Тело запроса дочитывается до отказа.** Если ответить `403`/`400`, не прочитав multipart-тело,
   сервер закрывает соединение с непрочитанными данными, и клиент изредка получает обрыв вместо
   ответа — это воспроизвелось на `runserver` под Windows. Поэтому view сначала разбирает тело, потом
   проверяет право на отзыв. (За прокси Render/Railway тело и так буферизуется, но так надёжнее.)

## Этап 9 — деплой

1. **Платформа — Render** (Blueprint `render.yaml`: веб-сервис + PostgreSQL на бесплатном плане).
   Сборка: `pip install` + `collectstatic`. Старт: `migrate` → `seed --github --if-empty` → `gunicorn`
   (2 воркера, `WEB_CONCURRENCY`). Health-check — `/api/v1/health/`. Миграции и seed стоят в команде
   старта, а не в `preDeployCommand`: на бесплатном плане его нет.
2. **Медиа — Cloudflare R2 через `django-storages` (S3-совместимый бэкенд).** У бесплатного Render нет
   постоянного диска, всё записанное в `media/` теряется при перезапуске (а бесплатный сервис
   засыпает и перезапускается часто). Почему R2, а не Cloudinary или диск Render:
   - `*.r2.dev` уже разрешён в `next.config` фронта, `NEXT_PUBLIC_MEDIA_URL` не нужен;
   - 10 ГБ и исходящий трафик бесплатно, S3-совместимый API: тот же код работает с AWS S3,
     Backblaze B2 и т.п.;
   - Cloudinary тоже разрешён во фронте, но для него нужен отдельный пакет со своей моделью URL,
     а платный диск Render не масштабируется на несколько инстансов.
   Настройка — `MEDIA_STORAGE=s3` и `S3_*`; файлы публичные, URL без подписи и срока жизни
   (`querystring_auth=False`, `custom_domain`), имена не перезаписываются (`file_overwrite=False`).
   **Запасной вариант без R2** (`MEDIA_STORAGE=local`): Django сам отдаёт `/media/` и при `DEBUG=False`,
   но фото пропадают при перезапуске. Годится только для проверки.
3. **Seed на проде одной командой: `python manage.py seed --github`.** Клона фронта на сервере нет, а
   копировать фронт в репозиторий бэкенда ТЗ запрещает. Поэтому `catalog.json` и картинки берутся из
   публичного репозитория фронта, **закреплённого на коммите `6457c04`** (с ним сверялся контракт):
   seed не изменится сам, если в `main` фронта что-то поменяют. Другой коммит — `--github <ref>`.
   Картинки качаются параллельно (8 потоков, ~10 с вместо ~70 с) и до транзакции с БД; уже
   загруженные в хранилище не скачиваются повторно. `--if-empty` ничего не делает, если товары уже
   есть: команда стоит в старте сервиса и не сбрасывает остатки и популярность при каждом пробуждении.
4. **Прод-настройки** включаются при `DEBUG=False`:
   - `SECURE_PROXY_SSL_HEADER` (TLS завершает прокси Render), secure-cookie сессии и CSRF;
   - refresh-cookie `Secure; SameSite=None`, строгие лимиты частоты;
   - статика через whitenoise (`CompressedManifestStaticFilesStorage`), без `SECRET_KEY` старт падает;
   - адрес сервиса из `RENDER_EXTERNAL_HOSTNAME` сам добавляется в `ALLOWED_HOSTS` и (с `https://`)
     в `CSRF_TRUSTED_ORIGINS`;
   - `CONN_HEALTH_CHECKS` для постоянных соединений с БД.
   `check --deploy` оставляет два предупреждения — `SECURE_SSL_REDIRECT` и `SECURE_HSTS_SECONDS`
   выключены по умолчанию: Render сам перенаправляет http → https, а HSTS включается переменной
   осознанно (его нельзя быстро отменить).
5. **Stripe необязателен.** Без `STRIPE_SECRET_KEY` заказ с `payment_method=card` не создаётся:
   `400 payment_method_unavailable` «Оплата картой онлайн сейчас недоступна. Выберите оплату при
   получении.». Иначе фронт создал бы заказ, получил ошибку на `checkout-session`, не очистил бы
   корзину, и повторное нажатие плодило бы неоплачиваемые заказы. Остальное (включая заказы
   «при получении») работает без ключей; `checkout-session` и вебхук без ключей отвечают `503`.
6. **`.env.example`**: необязательные переменные закомментированы. Раньше явные `THROTTLE_*=…` и
   пустой `THROTTLE_RELAXED=` (django-environ читает его как `False`) при копировании в `.env`
   отключали мягкие лимиты в разработке.
7. **Проверка прод-режима локально** (без деплоя): `check --deploy`, `collectstatic` и `runserver` с
   `DEBUG=False` на базе, заполненной `seed --github`. Проверены статика через whitenoise, `/media/`,
   `/api/docs/`, JSON-404, CORS для прод-домена фронта, cookie `SameSite=None; Secure`, отказ в заказе
   картой без Stripe. Прод-настройки (R2, Render-хост, cookie, лимиты) закреплены тестами
   `apps/core/tests/test_deploy.py`. Запустить сам gunicorn на Windows нельзя (он только для Unix) —
   он будет проверен первым деплоем.
